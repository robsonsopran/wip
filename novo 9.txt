Redefinição do Scheduler: Estrutura e Implementação
1. Introdução
A redefinição do scheduler baseia-se na utilização de um vetor contendo 161 tarefas (tasks GLOB_task[161]). Esse vetor é composto por:
•	32 tarefas executadas por frame;
•	1 tarefa nula (NULLTASK), que indica ao agendador que a execução deve ser interrompida;
•	As demais posições permanecem disponíveis para a definição de sequências de execução.
Com essa estrutura, é possível configurar qualquer sequência de execução para as tarefas, respeitando a restrição de que a ordem das tarefas se repete a cada frame.
2. Estrutura da Tarefa (task)
Cada elemento do vetor GLOB_task é do tipo task, definido conforme a seguinte estrutura:
Atributo	Tipo	Descrição
task.schedule	uint8_t	Define em quais frames do hiperperíodo (fixado em 5 frames) a tarefa será executada.
task.time	uint16_t	Indica o tempo de execução da tarefa.
task.main	void (*)()	Ponteiro para a função principal da tarefa.
Cada tarefa pode ser configurada de acordo com essas variáveis, permitindo a execução em momentos predefinidos dentro do hiperperíodo.
3. Preenchimento do Vetor de Tarefas
O vetor de 161 posições permite a execução de diferentes sequências de tarefas. Para garantir o pior caso, a aplicação deve definir 160 tarefas diferentes, cada uma rodando apenas uma vez por frame.
A última posição do vetor sempre deve conter uma NULLTASK para indicar ao agendador o fim do processamento.
4. Definição de Tarefas com Macro
A definição das tarefas utiliza um macro que especifica a execução em cada frame. O scheduler (valor booleano) define se a tarefa será executada em determinado frame.
Exemplo de Definição de Tarefa
 tasks task[numtask] {
    TASK(true, true, false, true, false, exemplotask),
    NULLTASK
 };
Nesse exemplo, a exemplotask será executada nos frames 1, 2 e 4.
5. Flexibilidade e Troca de Ordem de Execução
A mudança da ordem de execução é possível, mas pode resultar em ocupação adicional do vetor.
Exemplo de Definição com Ordem Alternada
 tasks task[numtask] {
    TASK(true, false, true, true, true, exemplotask1),
    TASK(true, true, true, true, true, exemplotask2),
    TASK(false, true, true, true, true, exemplotask1),
    NULLTASK
 };
Neste caso:
•	No frame 1, as tasks exemplotask1 e exemplotask2 serão executadas;
•	No frame 2, a ordem de execução será exemplotask2 seguida de exemplotask1.
6. Implementação do Novo Scheduler
Segue abaixo um exemplo não testado do scheduler da aplicação, adaptado para suportar a nova estrutura:
void scheduler_run() {
    for (int i = 0; i < 161; i++) {
        if (GLOB_task[i].main != NULL) {
            if (should_execute(GLOB_task[i])) {
                GLOB_task[i].main();
            }
        } else {
            break; // Encerra a execução ao encontrar NULLTASK
        }
    }
}
A função should_execute() é responsável por verificar se a tarefa deve ser executada no frame atual.
7. Conclusão
A nova estrutura do scheduler permite uma execução organizada e previsível das tarefas, garantindo que todas sejam processadas conforme o hiperperíodo fixado. A utilização de um vetor fixo e de macros para definição das tarefas simplifica a gestão e execução das funções dentro do sistema.



Redefinição do Scheduler
1. Introdução
O presente documento descreve a redefinição do agendador de tarefas (scheduler), que passa a operar com um vetor fixo de 161 tasks (tarefas). Esse novo modelo visa garantir a previsibilidade e a padronização da execução de tarefas dentro de um hiperperíodo fixo de 5 frames.
2. Estrutura do Scheduler
O agendador opera com um vetor de tarefas declarado como:
 tasks GLOB_task[161];
Esse vetor contém até 160 tarefas ativas e uma última posição reservada para a task nula (NULLTASK), que indica a interrupção do processamento. O tamanho do vetor é definido considerando o pior caso, ou seja, a necessidade de agendar 160 tarefas diferentes dentro de um hiperperíodo de 5 frames (32 tarefas por frame mais a task nula).
3. Estrutura da Tarefa (Task)
Cada tarefa segue uma estrutura fixa, composta por três elementos principais:
Campo	Tipo	Descrição
task.schedule	uint8_t	Define em quais frames a tarefa será executada.
task.time	uint16_t	Contém o tempo de execução da tarefa.
task.main	function*	Ponteiro para a função principal da tarefa.
Essa estrutura permite que a execução das tarefas seja configurada para cada frame, garantindo flexibilidade e controle sobre o fluxo de execução.
4. Definição e Declaração de Tarefas
Para definir cada tarefa dentro do vetor GLOB_task, utiliza-se um macro, que define os frames em que a tarefa será executada, além do ponteiro para sua função principal.
4.1 Exemplo de Declaração de uma Tarefa
 tasks task[numtask] {
 TASK(true, true, false, true, false, exemplotask),
 NULLTASK
 };
No exemplo acima, a exemplotask será executada nos frames 1, 2 e 4. A última posição do vetor contém a task nula, indicando o fim do processamento.
4.2 Exemplo de Sequência de Execução de Tarefas
Também é possível definir um conjunto de tarefas com diferentes sequências de execução, como ilustrado abaixo:
 tasks task[numtask] {
 TASK(true, false, true, true, true, exemplotask1),
 TASK(true, true, true, true, true, exemplotask2),
 TASK(false, true, true, true, true, exemplotask1),
 NULLTASK
 };
Nesse caso, a execução das tarefas ocorrerá conforme a seguinte tabela:
Frame	Tarefas Executadas
1	exemplotask1, exemplotask2
2	exemplotask2, exemplotask1
5. Considerações sobre a Mudança
5.1 Impacto na Eficiência do Scheduler
A principal vantagem dessa abordagem é a previsibilidade na execução das tarefas. No entanto, há um trade-off em termos de alocação de espaço no vetor. Alterar a ordem de execução pode exigir espaço adicional no vetor, reduzindo a quantidade de tarefas que podem ser alocadas.
5.2 Implementação no Scheduler Atual
Abaixo, segue um exemplo de implementação do scheduler modificado, adaptado para suportar a nova estrutura de agendamento:
void scheduler_run() {
    for (int i = 0; i < 161; i++) {
        if (GLOB_task[i].schedule) {
            GLOB_task[i].main();
        }
        if (GLOB_task[i] == NULLTASK) {
            break;
        }
    }
}
Esse novo modelo garante que o processamento das tarefas seja interrompido ao atingir a task nula.
6. Conclusão
A redefinição do scheduler para um modelo de 161 tarefas fixa garante previsibilidade e controle rigoroso sobre a execução de tarefas ao longo de um hiperperíodo de 5 frames. A estrutura de tarefas permite flexibilidade na configuração, embora haja uma restrição de espaço devido ao tamanho fixo do vetor. A implementação apresentada fornece um ponto de partida para a migração para o novo modelo.



Scheduler Redefinition: Structure and Implementation
1. Introduction
The scheduler redefinition is based on the use of an array containing 161 tasks (tasks GLOB_task[161]). This array consists of:
•	32 tasks executed per frame;
•	1 null task (NULLTASK), which indicates to the scheduler that execution should be stopped;
•	The remaining positions are available for defining execution sequences.
With this structure, it is possible to configure any execution sequence for the tasks, respecting the constraint that the order of the tasks repeats every frame.
2. Task Structure (task)
Each element of the GLOB_task array is of type task, defined according to the following structure:
Attribute	Type	Description
task.schedule	uint8_t	Defines in which frames of the hyperperiod (fixed at 5 frames) the task will be executed.
task.time	uint16_t	Indicates the task's execution time.
task.main	void (*)()	Pointer to the task’s main function.
Each task can be configured according to these variables, allowing execution at predefined moments within the hyperperiod.
3. Task Array Population
The 161-position array allows different execution sequences. To ensure the worst-case scenario, the application must define 160 different tasks, each running only once per frame.
The last position of the array must always contain a NULLTASK to indicate the end of processing to the scheduler.
4. Task Definition with Macro
The task definition uses a macro that specifies execution in each frame. The scheduler (boolean value) defines whether the task will be executed in a given frame.
Example of Task Definition
 tasks task[numtask] {
    TASK(true, true, false, true, false, exemplotask),
    NULLTASK
 };
In this example, exemplotask will be executed in frames 1, 2, and 4.
5. Flexibility and Execution Order Change
Changing the execution order is possible but may result in additional array usage.
Example of Definition with Alternating Order
 tasks task[numtask] {
    TASK(true, false, true, true, true, exemplotask1),
    TASK(true, true, true, true, true, exemplotask2),
    TASK(false, true, true, true, true, exemplotask1),
    NULLTASK
 };
In this case:
•	In frame 1, tasks exemplotask1 and exemplotask2 will be executed;
•	In frame 2, the execution order will be exemplotask2 followed by exemplotask1.
6. Implementation of the New Scheduler
Below is an untested example of the application's scheduler, adapted to support the new structure:
void scheduler_run() {
    for (int i = 0; i < 161; i++) {
        if (GLOB_task[i].main != NULL) {
            if (should_execute(GLOB_task[i])) {
                GLOB_task[i].main();
            }
        } else {
            break; // Ends execution upon encountering NULLTASK
        }
    }
}
The function should_execute() is responsible for verifying whether the task should be executed in the current frame.
7. Conclusion
The new scheduler structure allows an organized and predictable execution of tasks, ensuring that all are processed according to the fixed hyperperiod. The use of a fixed array and macros for task definition simplifies the management and execution of functions within the system.
